# プロダクトドキュメント作成のベストプラクティス

## 1. 全体像の理解
まず、提供されたテキスト（議事録など）全体を読み、以下の点を把握します。
*   **何故このプロジェクトは存在するのか？ (Why):** プロジェクトの根本的な目的やビジョンは何か。
*   **何を解決しようとしているのか？ (What):** 具体的な課題やニーズは何か。
*   **誰のために作るのか？ (Who):** ターゲットとなるユーザーは誰か。
*   **どのように実現するのか？ (How):** 主要な機能やアプローチは何か。

## 2. 各セクションの抽出ガイド

### 2.1. プロジェクトの概要
*   **背景:** 議論の中で「なぜ今これが必要なのか」「何が変わったのか」に言及している部分を探します。組織変更、市場の動向、技術的な負債などが該当します。
*   **目的:** 「〜することを目指す」「〜を実現したい」といった、プロジェクトの最終的なゴールに関する発言を抽出します。これは定性的なものであることが多いです。
*   **目標:** 目的をより具体的に、測定可能な形で表現している部分を探します。「〜のアクセス数をX%向上させる」「〜の時間をY分短縮する」といった、KPI（重要業績評価指標）に繋がりそうな部分が該当します。

### 2.2. ターゲットユーザー
議論の中で「従業員」「〜の部署の人」「〜という役割の人」など、プロダクトの利用者として言及されている人物像を特定します。どのような課題を抱えている人物として描かれているかに注目します。

### 2.3. 主要機能
テキストから、具体的な「できること」「ほしい機能」をリストアップします。
*   「〜できる仕組みがほしい」「〜を一覧で見たい」「〜を申請できるようにする」といった発言が機能のヒントになります。
*   複数の関連する発言を、一つの機能としてまとめることを検討します。
*   機能には `F-01`, `F-02` のように一意のIDを割り振ります。

### 2.4. 各機能の詳細
*   **説明:** 抽出した機能が「何をするものか」を具体的に説明します。
*   **ユーザーにとっての価値:** その機能を使うことで、ユーザーのどのような課題が解決され、どのようなメリットがあるのかを記述します。
*   **受け入れ基準:** その機能が「完成した」と判断できるための具体的な条件を記述します。「ユーザーが〜の操作をしたとき、〜という結果が表示される」のように、客観的に検証可能な形で記述することが重要です。

### 2.5. 非機能要件
明示的に議論されていなくても、文脈から読み取れる要件を抽出します。
*   **パフォーマンス:** 「もっと速く表示したい」「大量のデータでも扱えるように」といった発言。
*   **セキュリティ:** 個人情報や機密情報の取り扱いに関する言及。
*   **ユーザビリティ:** 「もっと簡単に使えるように」「直感的に分かるように」といった発言。
*   **運用・保守:** 「運用負荷を下げたい」「自動で更新されるように」といった言及。

## 3. 記述の際の注意点
*   **客観性:** 個人的な解釈を避け、あくまでテキストに基づいた情報を記述します。
*   **明確さ:** 曖昧な表現を避け、誰が読んでも同じように理解できる言葉で記述します。
*   **一貫性:** ドキュメント全体で用語や表現を統一します。
