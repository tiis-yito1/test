# Git Operations

ユーザーの明示的な指示に基づき、staging・commit を正しい規約に沿って実行するスキル。

**重要**: このスキルはユーザーからの明示的な依頼があった場合にのみ使用する。
AI が自発的に commit, push, branch 作成等の Git 操作を実行することは禁止されている。

---

## ステージング判断

### ステージング対象

- `tasks/` 配下の成果物（spec.md, plan.md）
- `dits-portalapp/` 配下の実装コード・テストコード
- `.gemini/` 配下の設定ファイル（ユーザーが変更を指示した場合のみ）

### ステージング禁止

以下のファイルは絶対にステージングしない:

- `.env`, `.env.*` — 環境変数ファイル
- 認証情報・シークレットを含むファイル（API キー、トークン等）
- `appsettings.*.json` のうちシークレットを含むもの

### 要確認（ユーザー承認必須）

- `docs/` 配下のファイル — 仕様書は READ ONLY が原則。変更が必要な場合はユーザーに確認する。
- DB マイグレーションファイル — スキーマ変更は破壊的操作に該当するため、必ず確認を取る。

## コミットメッセージ規約

### プレフィックス

| プレフィックス | 用途 | 例 |
| :--- | :--- | :--- |
| `[add]` | 新規機能追加 | `[add] イベントカレンダーの検索機能追加` |
| `[update]` | 機能修正（バグ修正ではない） | `[update] 検索機能リファクタリング` |
| `[fix]` | バグ・不具合修正 | `[fix] 登録機能バグ修正` |
| `[remove]` | 削除 | `[remove] ログイン機能廃止により関係ファイル削除` |

### ルール

- 本文は**日本語**で記述する。
- 「何をしたか」を簡潔に記述する（1 行目に収める）。
- 複数の変更を含む場合は、最も主要な変更を 1 行目に書き、詳細は本文に記述する。

---

## ブランチ命名規約

`feature/{add|update|fix|remove}-英語の機能名`

- ブランチ名は**全て英語**。
- 例: `feature/add-event-search`, `feature/fix-calendar-display`

---

## 操作手順

ユーザーからコミット指示を受けた場合、以下の手順で実行する:

1. `git status` で変更ファイルを確認し、ユーザーに提示する。
2. ステージング対象・禁止のルールに従い、`git add` する対象を提案する。
3. コミットメッセージ案を提示する。
4. ユーザーの承認を得てから `git commit` を実行する。
5. **`git push` はユーザーの明示的な指示がない限り実行しない。**
