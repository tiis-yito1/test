# 変更点分析ガイド

このガイドは、議事録や変更要求書などの非構造化ドキュメントから、仕様変更に必要な情報を抽出するための指針です。

## 分析のステップ

1.  **目的の特定:** まず、このドキュメントが「何のためのものか」を理解します（例：新機能のブレスト、既存機能の仕様変更会議）。

2.  **決定事項の抽出:** 「決定」「結論」「→」「対応」などのキーワードや、明確な指示を示す表現に注目し、何が決定されたのかをリストアップします。

3.  **変更箇所の特定:**
    *   **変更対象:** 何（どの機能、どの画面、どの項目）についての変更か？
    *   **変更前 (As-Is):** 現在の仕様はどうなっているか？（記載があれば）
    *   **変更後 (To-Be):** 新しい仕様はどうなるべきか？

4.  **変更理由の把握:** なぜその変更が必要なのか？（例：「ユーザーの離脱率が高いため」「法改正への対応」など）。理由を理解すると、より文脈に合った修正ができます。

5.  **情報のマッピング:** 抽出した情報を、以下の観点で整理します。

    | 観点 | 抽出例 |
    | :--- | :--- |
    | **プロジェクト/機能名** | 「デジ戦ポータル」を「ProjectGENA」に名称変更。 |
    | **画面項目の変更** | ログイン画面から「パスワードを記憶する」チェックボックスを削除。 |
    | **ロジックの変更** | ポイント計算ロジックを「購入金額の1%」から「200円ごとに1ポイント」に変更。 |
    | **テキスト/文言の変更** | エラーメッセージ「失敗しました」を「接続に失敗しました。時間をおいて再度お試しください」に変更。 |
    | **非機能要件の変更** | APIの応答時間目標を「300ms」から「200ms」に短縮。 |

この分析結果を基に、変更点をユーザーに要約・確認し、仕様書のどこをどのように修正すべきかを判断します。
