# Structural Improvement（構造改善）

外部の振る舞いを変更せずに、既存コードの内部品質を向上させるためのワークフロー。
通常の SDD ワークフロー（sdd-implementer）とは **Phase 1 の情報源が異なる**。

> **重要な前提**: このスキルは「振る舞いを変えない」タスク専用。
> 新機能の追加や振る舞いの変更を伴う場合は `sdd-implementer` Skill を使用すること。

---

## sdd-implementer との関係

| | sdd-implementer | structural-improvement |
| :--- | :--- | :--- |
| **目的** | 新しい振る舞いを実装する | 既存の振る舞いを保持しつつ構造を改善する |
| **Phase 1 の情報源** | `docs/`（仕様書） | 既存コード + テスト |
| **Phase 2 (TDD)** | 共通（sdd-implementer に従う） | 共通（sdd-implementer に従う） |
| **Phase 3 (Verification)** | 共通（sdd-implementer に従う） | 共通 + 振る舞い保持の確認 |
| **Coding Standards** | sdd-implementer を適用 | sdd-implementer を適用 |

---

## Phase 1: 現状把握と改善設計

### Step 1: 対象コードの振る舞いを把握する

- 対象コードと既存テストを読み、**現在の外部的な振る舞い**を把握する。
- 外部的な振る舞いとは: 公開インターフェース（API、関数シグネチャ、戻り値、副作用）。
- 内部の実装詳細（private メソッドの構造等）は改善対象であり、保持対象ではない。

### Step 2: テストカバレッジを評価する

- 対象コードの外部的な振る舞いが、既存テストで十分にカバーされているか確認する。
- **十分でない場合**: 振る舞いを固定するテスト（Characterization Test）の追加が必要。
  - テスト追加のスコープが大きくなる場合は、**ユーザーに相談して対象を絞る**。
  - 目安: テスト追加だけで 1 日以上かかりそうなら、構造改善の前に「テスト追加タスク」として分離を提案する。

### Step 3: spec.md を作成する

`sdd-implementer` の `spec-template.md` をベースに、以下の観点で作成する:

| spec.md セクション | 構造改善での記述内容 |
| :--- | :--- |
| §1 スコープ | 改善対象のモジュール・ファイル |
| §1 スコープ外 | 振る舞いの変更、機能追加は明示的に除外 |
| §3 振る舞い定義 | **保持する振る舞い**（既存テストで検証される動作） |
| §5 設計 | **改善目標**（何をどう改善するか: 分割、命名、依存整理 等） |
| §5.2 Rationale | なぜこの構造改善が必要か（可読性、保守性、テスタビリティ等） |
| §7 受け入れ基準 | 全既存テストが Green のまま + 改善目標の達成 |

**ユーザーの承認を得てから Phase 2 に進むこと。**

### Step 4: plan.md を作成する

`sdd-implementer` の `plan-template.md` に従い、タスクリストを作成する。

---

## Phase 2: TDD による構造改善

`sdd-implementer` の Phase 2 に従う。ただし以下の制約を追加する:

- **各ステップの後、既存テストが全て Green であることを確認する。**
- Red になった場合、振る舞いを変更してしまった可能性がある。変更を巻き戻して原因を特定すること。
- 新しいテストを追加する場合は、構造改善後の設計に対するテスト（例: 分割後の個別モジュールのテスト）に限定する。

---

## Phase 3: 検証

`sdd-implementer` の Phase 3 に加え、以下を確認する:

- **既存テストが全て Green である**（振る舞いが保持されている）。
- spec.md §5 の改善目標が達成されている。
- `code-reviewer` Skill のチェックリストを適用する。
